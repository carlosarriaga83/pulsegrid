# Servo ESP32

Firmware MicroPython para el controlador Waveshare Servo Driver con ESP32 y servos ST/STS. El dispositivo se administra por Pulsegrid y las actualizaciones deben publicarse y aplicarse por OTA; no se presupone acceso USB/COM.

El perfil usa un unico `config.py` con Wi-Fi, API URL HTTPS, `DEVICE_CODE`, Device ID, comandos y sentido. El código se deriva determinísticamente de la MAC para que pueda volver a calcularse en el quemador; no es un secreto: cualquiera que conozca la MAC puede calcularlo e imitar el dispositivo. El cloud guarda solo su hash. La API key de usuario, si se usa para integraciones externas, no es una credencial del firmware.

Archivos incluidos en un release OTA: `main.py`, `cloud_client.py`, `board_led.py`, `captive_portal.py`, `cortina.py`, `servo_calibration.py`, `stservo.py`, `boot.py`, `ota_boot.py`, `pulsegrid_ota.py` y `wifi_recovery.py`. `config.py` se genera durante la provision y no se reemplaza por OTA.

`main.py` ejecuta localmente el control y el muestreo del encoder en ciclos de 10 ms. El cliente abre HTTPS/TLS por solicitud y envía `Connection: close`: en la prueba desde COM6, el proxy del proveedor respondió así, pero dejó sin respuesta solicitudes `keep-alive`; no reutilizamos una conexión que atasca el sondeo de comandos. El DNS intenta hasta cuatro direcciones IPv4/IPv6 retornadas por el hostname y pasa a la siguiente si una no conecta o falla TLS, manteniendo el hostname original para SNI. Durante el movimiento solo se consultan comandos prioritarios de parada/cancelación, sin telemetría ni comandos generales; el ACK del comando que inició el movimiento se difiere hasta que el control local termina de leer el encoder y detener el servo. Así, HTTPS no retrasa el muestreo local ni la parada, y la parada remota sigue disponible. Para reservar heap interno del ESP-IDF para TLS, el portal local no arranca en operación normal con Wi-Fi y código de dispositivo configurados; sí arranca durante recuperación, provisionamiento o sin Wi-Fi. Para volver a abrir el portal/AP, corta y restablece la alimentación tres veces rápidamente para entrar en recuperación. El portal local (`http://<IP-del-ESP>/` o `http://192.168.4.1/` desde el AP) sirve únicamente para guardar credenciales de Wi-Fi; la calibración y el control se realizan desde Pulsegrid. El portal usa un hilo de 8 KB y limita las solicitudes a 1024 bytes. Los sockets cloud usan buffers predeterminados: en COM6 se observó handshake TLS exitoso con valores predeterminados y fallos al forzarlos a 512 bytes. El cliente registra las fases de DNS, TCP y handshake, además de la memoria libre del heap MicroPython y ESP-IDF.

Para ESP32 que aún fallen durante el handshake, hay un perfil MicroPython de bajo consumo TLS en [micropython-board/README.md](micropython-board/README.md); requiere compilar y flashear una imagen personalizada, no se instala mediante OTA.

La placa Waveshare usa un RGB WS2812 en GPIO23. `board_led.py` controla los píxeles 0 y 1 del indicador integrado: verde cuando hay respuesta reciente de Pulsegrid, amarillo durante el aprovisionamiento (sin código registrado), rojo si el dispositivo registrado no tiene Wi-Fi o el cloud lleva más de 30 s sin responder y ámbar intermitente durante la recuperación Wi-Fi. Para abrir el portal aunque la red guardada todavía conecte, corta y restablece la alimentación tres veces rápidamente; el AP de configuración permanece activo hasta guardar las nuevas credenciales. La secuencia se cancela tras 30 s de funcionamiento estable. `led.configure` habilita o apaga la indicación sin alterar el estado detectado.

Los comandos generales ESP se consultan cada segundo y cada 200 ms durante la calibración cuando el mecanismo está detenido; durante movimiento se consulta solo la cola prioritaria de parada/cancelación cada segundo. La telemetría se envía cada 2 s normalmente y cada 500 ms durante la calibración, únicamente en reposo y usando snapshots del encoder leídos por el bucle local. Desde `2026.10.21.servo-r24`, la telemetría también continúa cuando queda activo un indicador de calibración segura, para que el cloud reciba la versión y el estado actuales y permita diagnosticar/reiniciar ese flujo. Desde `2026.10.21.servo-r25`, el porcentaje considera el lado de montaje configurado para cada servo; selecciona el lado físico correcto al aplicar la calibración geométrica de cada servo. Desde `2026.10.21.servo-r26`, cada porcentaje se trata como setpoint absoluto comparado con la posición del encoder, incluso si el setpoint coincide con el último comando registrado. Desde `2026.10.21.servo-r27`, aplicar una calibración cloud reemplaza por completo el registro de calibración anterior, descarta las referencias de calibración antiguas y vuelve el setpoint guardado a 50% sin mover el motor; conserva el origen absoluto fiable del encoder. Desde `2026.10.21.servo-r28`, los ACK de movimiento esperan a que termine la tarea del encoder y reportan `failed` ante timeout o parada prematura, en lugar de confirmar como exitoso un comando que solo fue aceptado por el firmware. Desde `2026.10.21.servo-r29`, los movimientos normales vuelven a retener el encoder en modo de posición al detener la rueda; un objetivo que ya coincide con el porcentaje medido no vuelve a arrancar el motor, y el comando se rechaza si ningún servo necesita moverse.

La calibración Servo se configura únicamente desde Pulsegrid: el cloud calcula las vueltas a partir de las medidas de la ventana, tubo y paño, valida el cálculo y envía `blind.cloudCalibrationConfigure`. El firmware vuelve a comprobar el cálculo y guarda un rango geométrico estimado de ±40% de las vueltas calculadas, centrado en la posición absoluta actual del encoder. Esto no detecta topes mecánicos, fuerza ni atascos, y no inicia movimiento. Si `position_recovery_required` indica que la posición no es fiable, primero debe recuperarse una referencia del encoder; la calibración se rechaza hasta entonces. El botón de recuperación cloud requiere colocar manualmente la cortina cerca de la mitad; `blind.encoderReferenceRecover` guarda esa posición como origen relativo y no mueve el motor. La calibración posterior queda centrada en ese origen. La recuperación requiere firmware Servo r23 o posterior y conexión al cloud. El sentido se corrige con el toggle de dirección del dispositivo en Pulsegrid, que invierte la correspondencia entre porcentaje y los dos extremos guardados sin mover el motor ni cambiar la envolvente numérica.

El adaptador `cortina.py` mantiene la superficie de movimiento del cloud (`curtain.open`, `curtain.close`, `curtain.stop`, `curtain.move`) sobre el bus STServo y persiste los extremos estimados, medidas, sentido, porcentaje objetivo y recorrido absoluto. Los estados `blind_state.py` y `multiturn_state.py` quedan fuera de OTA y de la limpieza del perfil del quemador; sus escrituras usan temporal y respaldo para recuperarse de un reset durante el guardado. Si un reset interrumpe un movimiento, se conserva la configuración pero la posición queda marcada para recuperación. Un borrado completo de flash sí elimina esos archivos.

OTA ya escribe cada archivo en bloques de 512 bytes directamente al staging de flash (`.pulsegrid_ota/stage`); no carga el firmware completo en RAM. Acepta `Content-Length` y `chunked`, valida tamaño y SHA-256 antes de activar el release y conserva backup transaccional hasta confirmar el arranque. Tiene timeout de 30 s, reintenta una vez ante timeout, importa TLS bajo demanda y recolecta memoria tras abrir TCP y antes del handshake; si falla, registra la fase exacta. Alimenta el watchdog durante la operación normal. Los archivos persistentes de calibración no forman parte del release. El cliente cloud también recolecta antes del handshake y reintenta el transporte tras un segundo; toda autenticación del dispositivo viaja exclusivamente por HTTPS.
